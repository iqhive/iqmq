    redis¶

    Maturity: Experimental · Tier: 2 · Module: github.com/iqhive/iqmq/drivers/redis · Profile: streams

    Client & version policy¶

    The native baselines for this driver live in benchmarks/native-baselines/ and measure the clients below against the harness's redis image (make bench-native CLIENTS="rueidis goredis"). A driver number is only comparable with a baseline taken from the same client version, broker version and confirmation boundary, so the pins move together; each baseline's package comment records the settlement boundary it measures as well.

    Baseline Client Pinned version Confirmation boundary
    rueidis github.com/redis/rueidis github.com/redis/rueidis@v1.0.79 XADD reply from the server (appendfsync everysec, no WAIT)
    goredis github.com/redis/go-redis/v9 github.com/redis/go-redis/v9@v9.23.0 XADD reply from the server (appendfsync everysec, no WAIT)

    Verified facts¶

    Checked while building the native baselines; re-verify when a pin moves.

    • reclaim support. XAUTOCLAIM, which a stream driver needs to reclaim entries from dead consumers without scanning the pending-entries list, requires Redis 6.2 or newer; the harness pins redis 7.4 and offers valkey 8.1 as a matrix image. Verified against: Redis command documentation (XAUTOCLAIM, since 6.2.0); conformance/harness/images.go.
    • rueidis argument model. rueidis builds commands from string arguments, so a []byte payload must go through rueidis.BinaryString — the documented conversion that does not copy — and its auto-pipelining lets one connection carry a whole batch through DoMulti. Verified against: rueidis v1.0.77 binary.go:17 and client.go:89.
    • value size. A Redis string value, and therefore a stream field value, is limited to 512 MiB; the practical limit for a message payload is set by memory and by proto-max-bulk-len (512 MiB by default), not by the client. Verified against: Redis data-type documentation; redis.conf default.
    • XACK does not check ownership. XACK key group id removes the entry from the group's pending-entries list whoever is holding it and whatever its delivery counter is. There is no token, no receipt and no lease, which is why this driver's acknowledgement is a guarded script — see Ack / nack / extend mapping. Verified against: Redis 7.4 XACK documentation and behaviour; the ack guard's own suite.
    • Redis grants no lease and redelivers nothing. A consumer group hands an entry to a consumer and then does nothing about it for ever. Redelivery is entirely the client's, through XAUTOCLAIM/XCLAIM on idle time, which is why the reclaim loop is mandatory rather than an optimisation. Verified against: Redis 7.4 consumer-group documentation.
    • XCLAIM ... JUSTID does not increment the delivery counter, and a plain XCLAIM does. That is what makes JUSTID usable as a lease extension and a plain claim unusable as one. Verified against: Redis 7.4 XCLAIM documentation.
    • XCLAIM with min-idle 0 claims an entry however recently it was delivered. So an extension written as a bare XCLAIM steals the entry from its current holder; FuzzRedisReclaimer found it in 1.3 seconds. Verified against: Redis 7.4 XCLAIM semantics.
    • XGROUP DELCONSUMER deletes the consumer's pending entries with the consumer. A tidy-up that removed a consumer still holding entries would delete those messages from the group for ever. Verified against: Redis 7.4 XGROUP DELCONSUMER documentation.
    • WAITAOF arrived in 7.2 and fails outright when appendonly is no. It is therefore the conditional durable boundary, and both conditions are facts about the deployment rather than things a caller can turn on. On 7.0 it is an unknown command, and the XADD in front of it has landed by then, so the driver used to accept ConfirmDurable there and fail every durable publication as ambiguous. Verified against: WAITAOF documentation ("Available since 7.2.0"); redis-cli WAITAOF 1 0 100 on redis:7.0.15 (ERR unknown command) and redis:7.2.17 (1 0); TestDurableConfirmFlipsWithTheServer.
    • A master that cannot write refuses every write until the condition clears. With min-replicas-to-write unmet it answers NOREPLICAS; after a failed RDB save under stop-writes-on-bgsave-error yes (the default), or a failed AOF write, it answers MISCONF. The refusal comes before the command runs, and a script stops at its first write, so nothing was written, and the condition clears without the client (a replica catches up, the disk has room again). Both are CodeUnavailable, retryable and definite, for a publication, a fetch and a settlement alike; they used to be CodeUnknown and not retryable. Verified against: Redis 7.4 server.c (shared.noreplicaserr, shared.bgsaveerr); TestAMasterThatCannotWriteIsRetryable, and a real 7.4 server with min-replicas-to-write 1 and with /data read-only.
    • An ACL refusal inside a script carries no NOPERM. A command the ACL refuses inside a script is answered ACL failure in script: User <u> has no permissions to run the '<c>' command on Redis 7 (go-redis keeps a leading ERR), and The user executing the script can't run this command or subcommand (or can't access at least one of the keys) on 6.2, inside its script-error wrapper, while a refusal of the script's own keys, checked before it runs, is NOPERM. Every settlement and the consumer removal are scripts, so both are CodeForbidden and not retryable; they used to be CodeUnknown. The acknowledgement, the extension and the consumer removal write with one command, so their refusal is definite. A negative settlement's script writes before its XACK (the re-add, the delayed park, the dead-letter copy), and Redis keeps a script's earlier writes when a later command fails, so its refusal has an unknown outcome: on a real 7.4 a re-add whose XACK the ACL refused left the copy in the stream. A reply names users, keys and groups a caller chose, so every rule matches the reply's error code, its first word (after the ERR go-redis keeps, and the wrapper 6.2 puts round an error inside a script with the - it leaves on a server refusal there, as in -NOREPLICAS, -MISCONF, -OOM and -READONLY), or for a generic ERR reply the fixed text it begins with. The rules used to search the whole text: a NOPERM for a user called TASK or LOADER was matched by the ASK or LOADING rule and reported as Unavailable and retryable, and a NOGROUP naming a group called NOPERM-audit was Forbidden rather than NotFound. Verified against: Redis 7.4 script.c (scriptVerifyACL); real 7.4 with a user +@all -xack, both clients; TestAnACLRefusalInsideAScriptIsForbidden.
    • XADD refuses an entry with no field-value pairs. So a message with nothing in it still has to produce a field. Verified against: Redis 7.4 XADD behaviour; the publish/roundtrip-bodies scenario.
    • A stream entry's fields are an ORDERED list of binary-safe strings, and a stream identifier's high half is the publication time in milliseconds. The first is why this driver needs no portable envelope; the second is why seek-by-time is a real position rather than an approximation. Verified against: Redis 7.4 streams documentation; RESP bulk-string encoding.
    • Redis Cluster refuses a script whose keys are on two hash slots (CROSSSLOT). That is why every key of a topic carries the topic's hash tag. Verified against: Redis Cluster specification; FuzzRedisKeyNaming.

    Minimum server: Redis 6.2. The driver refuses to open against anything older, and the refusal is not a policy preference: the mandatory pending-entries reclaim loop is XAUTOCLAIM, and without that loop nothing on this broker redelivers — so opening against 5.x would advertise at-least-once delivery on a server that has at-most-once. When the server will not report a version (a managed Redis with INFO behind an ACL) the driver asks it directly whether XAUTOCLAIM exists, rather than refusing a server it can actually use.

    Valkey is supported as the same profile. It reports valkey_version beside redis_version and the driver prefers its own key: a Valkey reporting redis_version: 7.2.4 for compatibility is not a Redis 7.2.4, and the version matrix has to tell them apart.

    Topic / subscription mapping¶

    iqmq Redis Streams Notes
    Topic stream key {topic} hash-tagged, so every shard of a topic is on one cluster slot
    Topic shard i > 0 {topic}:<i> shard 0 is the bare tag, so adding a partition never renames the stream that already holds every message
    Config.KeyPrefix inside the tag: {prefix.topic} a prefix OUTSIDE the tag would leave the tag as the bare topic, so two deployments' same-named topics would collide on one slot
    ConsumerConfig.Subscription consumer group two consumers of one subscription compete; two subscriptions each receive everything
    one Source one consumer name <prefix>-<sub>-<nonce>, unique per source instance — see Ack / nack / extend mapping
    Message.Key chooses the shard (FNV-1a) and travels in the k field, so it survives the round trip
    dead-letter destination Config.DeadLetterTopic or {topic} + Config.DeadLetterSuffix neither is set by default; see Dead-letter queue
    delayed redelivery (zset arm) {topic}:delayed, {topic}:<i>:delayed a sorted set per shard, scored by deliver-at time

    A topic is one cluster slot, and that is a trade rather than an oversight. Every key of a topic carries the topic's hash tag, so shards buy ordering lanes and parallel consumers within a subscription and do not spread a topic across a cluster's nodes. The price buys the thing this driver cannot do without: the dead-letter move, the delayed park and the delayed release are each one Lua script touching two of a topic's keys, and a cluster refuses a script whose keys are on two slots. A single very hot topic scales by being split into several topics, not by adding partitions.

    Config.Partitions is a client-side setting with no server-side record. A deployment that changes it changes which shard a key hashes to, so messages already in the old shards stay there and per-key ordering is broken across the change. Treat it as a topic's shape, decided once.

    Entry field layout¶

    Field Content
    b the body. Absent for a nil body, present-and-empty for an empty one
    k the key, with the same nil-versus-empty rule
    t the logical topic
    h:<n> header n in publication order, framed as <decimal key length>:<key><value>
    p:<n> typed property n: 0 identifier, 1 content type, 2 content encoding, 3 correlation id, 4 causation id, 5 reply-to, 6 created-at as <seconds>,<nanoseconds>
    x:* the driver's own bookkeeping, never message content: x:a the carried attempt count, x:d a deliver-at time, x:e the marker that makes an otherwise empty message publishable, x:env = 1 on an entry whose body is the portable envelope

    The header framing is a length and not a separator because every byte — the separator included — is a byte a header value may contain. The property indices are part of the wire format and are append-only.

    p:6 is two integers rather than one nanosecond count: a single unix-nanosecond count overflows an int64 outside 1678–2262, and a time a caller can construct must not become a different time on the way back. The one thing the round trip does not preserve is the LOCATION: an entry carries none, so a CreatedAt set in a named zone comes back as the same instant in UTC.

    x:e exists because XADD refuses an entry with no field-value pairs, and a message with a nil body, a nil key, no topic, no headers and no properties encodes to nothing.

    Publish path & confirmation boundary¶

    Publish is XADD <key> [NOMKSTREAM] [MAXLEN ~ n] * <fields...>, in this order:

    1. the per-call controls this broker cannot honour are refused, before any I/O;
    2. the entry layout's limits are checked, in every metadata mode;
    3. the shard is chosen: an explicit partition, then the key's hash, then 0;
    4. the XADD goes to the server;
    5. under ConfirmDurable only, WAITAOF waits for the append-only file.
    Mode Boundary
    ConfirmNone the XADD is written; its reply is not waited for
    ConfirmAccepted (default) XADD's reply: the entry is in the server's memory and will be served to a reader. Nothing about disk is implied.
    ConfirmDurable WAITAOF <local> <replicas> <timeout>: the write has reached that many append-only files

    ConfirmDurable is conditional and is refused at construction on a server that cannot define the boundary: Redis below 7.2, or appendonly no. A publisher that discovered it at its first message would already have told the application it was safe to forget the data.

    A WAITAOF that comes back short of the number asked for is reported as an ambiguous outcome, not a failure: the entry IS in the stream and may yet be fsynced, so a caller told "failed" would republish and duplicate it. A WAITAOF that fails outright after its XADD landed (LOADING, READONLY, or a reply the driver cannot read) is ambiguous for the same reason. It keeps its code, so you can still see why.

    DurableTimeout is the bound the WAITAOF gets. It is sent as a command that parks at the server, as a blocking read is, so the connection's own read bound does not cut it, and the whole durable round trip, a batch's XADDs included, is bounded by DurableTimeout plus DialTimeout, or by the caller's context when that ends sooner. Earlier versions sent it as an ordinary command: rueidis cut its reply at the connection's write timeout (ten seconds), and the go-redis client the driver dials at Block plus DialTimeout, so a WAITAOF answered in time under a longer DurableTimeout failed with an i/o timeout, ambiguous, and dropped the connection. The go-redis client the driver dials now reads under the longer of Block and DurableTimeout, plus DialTimeout. A go-redis client handed to OpenWithClient keeps its own ReadTimeout, and the driver fits DurableTimeout inside it as it fits Block: a default one is shortened, and one you set that does not fit is refused when the backend opens.

    A command whose dial connected nowhere was never written, so its failure is definite and retryable: a publication may be repeated, and a settlement leaves the delivery settleable. Both clients answer commands with such a dial's error once the server has gone (refused, unreachable, a connect that timed out, a name that did not resolve), and neither sends a command this driver builds a second time. A failure on a connection that was made, such as a reset or an EOF, stays ambiguous for a publication and an unknown outcome for a settlement. Earlier versions read a refused dial as possibly applied too, so every publication while the server was down was ambiguous and not retryable, and every settlement went unknown for good.

    Leave ConnLifetime unset on a rueidis client you hand to OpenWithClient. It is the one rueidis setting under which a command this driver builds is sent twice: when a connection's lifetime ends while a command it wrote waits more than a second for its reply, rueidis sends the command again on a new connection, whatever it is. A publication is then stored twice under one success, and a redial the server refuses reads as a command that never left. rueidis cannot turn this off for one command, and the driver cannot see the setting on a client it is handed. The client the driver dials itself sets no lifetime.

    A publication or settlement still waiting for its reply when the backend closes is an unknown outcome, still CodeClosed. rueidis's close waits a second for the replies in flight, then closes the connection and answers each command still waiting with its closing error, whether it was written or not. Earlier versions reported that as a definite failure, so a caller that published the message again could store it twice. A publication made once the close has begun is refused before anything is sent. rueidis gives the same answer when it closes a connection itself, outside any close: a Sentinel failover closes the old master's, and a cluster client one to a node its slot map dropped. It also gives it, unwritten, to a call made on a connection it has just closed, and the driver cannot tell that from the written case, so it too reads as unknown. The go-redis arm reports a command in flight at the close as an ambiguous read error, as it did before.

    Batch publication is native and NOT atomic. rueidis pipelines the whole batch into one flush, so a hundred messages cost one round trip; Redis executes pipelined commands independently, so a partial failure is a partial batch. The result is index-aligned with the input. FeatureAtomicBatchPublish is unsupported, and a batch containing a message the limits refuse is refused in full before anything is written — the specification puts the refusal before the write, and half a caller's batch in the stream is worse than none of it.

    Refused before any I/O: Delay, DeliverAt, TTL, Priority, DedupKey, a partition the topic does not have, and any message over the entry layout's limits.

    The message body is copied, and the go-redis arm does not copy it¶

    This driver copies the message body into every command it sends; drivers/redis/goredis does not. It is a statement rather than a performance note, and it is the reason for part of the breach on this profile.

    rueidis queues a command for a background writer, and a cancelled Do returns ctx.Err() while the command is still in that queue — _backgroundWrite then writes its tokens from another goroutine, after Publish has returned. gives the caller its buffer back at that moment, so a body that aliased the caller's slice would put whatever the caller wrote next on the wire: a corrupt entry in the stream, reported as nothing. go-redis writes in the calling goroutine, so the body is on the wire before Publish returns and aliasing is safe there.

    What this means for you: on this driver you may reuse a body buffer freely. On the go-redis arm you may too — the specification is the same promise on both — but a redis.Hook you install through its OpenWithClient that STORES the Cmder and reads its arguments after its own call returns must copy what it stores, because the body argument is the publisher's buffer and the publisher has it back.

    Delay is refused even though the zset nack arm can hold a redelivery back, and the distinction is not pedantry: a delayed publication is a message that must not be deliverable yet, and a delayed redelivery is a message that has already been delivered once. Reusing the retry machinery for the first would mean acknowledging a message nobody has consumed. TTL is refused even though a stream has MAXLEN: MAXLEN is the whole stream's retention, measured in entries, and cannot expire one message out of the middle.

    Consume path¶

    XREADGROUP GROUP <group> <consumer> COUNT <prefetch> BLOCK <block> STREAMS <keys...> ><...>, plus two background loops.

    • COUNT is ConsumerConfig.Prefetch, resolved by the core.
    • BLOCK is Config.Block (default 5 s) and is never zero: BLOCK 0 means for ever in Redis, and a fetch that cannot be woken is what the specification forbids. Close is therefore prompt to within one block. The read runs under a context the source's close ends. rueidis ends a blocking read whose context has no deadline as that context ends, closing the read's connection, so a close of a Receive with no deadline (a runner's fetch, Receive(context.Background(), ...)) is prompt at once. Under a context with a deadline rueidis runs the read on its connection without watching the context, and go-redis never watches it, so then the close waits for the read to return, up to one block.
    • A read blocks no longer than the sweep interval. What a sweep round claims waits in the source's buffer until the read a Fetch is parked in returns, and nothing can wake that read short of closing its connection. The block used to be the whole of Config.Block, which is longer than the interval whenever the sweep runs more often than every 5 s (by default, for any deadline under 15 s), so a redelivery waited out the block. An idle consumer with a short deadline sends more reads as a result: one per interval rather than one per Config.Block.
    • A read ends 150ms before its Fetch's deadline. Redis answers a block not when it ends but at the next tick of its timer, 10 a second at the default hz, so the margin is that tick and 50ms for the reply. A read that ran into the deadline cost its connection on both clients (rueidis and go-redis close a connection whose blocking read they gave up on), so a pull loop with a 100ms deadline dialled 10 times a second when idle; and what the server handed such a read in its last moment was pending to this consumer and never delivered, until the sweep claimed it a deadline later as attempt 2. With less than 150ms left a Fetch reads once without blocking and then waits for the sweep, its context or Close, so a message published in that last stretch of an idle Fetch goes to the next one. Under the stop arm a settlement made while a shard is held wakes it too, because it may lift the hold; any other settlement does not. Every Ack, Nack and Extend used to wake it, so it read again once for each settlement its caller made meanwhile. A link whose replies take longer than about 50ms can still lose a read to the deadline.
    • NOACK is never set. It is at-most-once delivery: the pending-entries list is where a redelivery comes from, so a NOACK read is a read whose messages cannot be recovered from a crash.
    • The reclaim sweep runs every Config.ClaimInterval (default one third of the deadline) and is mandatory — see the next section. Each round is one XPENDING and one XAUTOCLAIM per shard, pipelined, and one XCLAIM per shard in a second round trip when the XPENDING lists an expired entry the XAUTOCLAIM did not reach (see below). Under the stop nack arm a source sweeps at least every third of its own acknowledgement deadline, which can be shorter than the backend's (see Delays), though never more often than every 10ms on that account.
    • A round claims only for a caller that is fetching: one with a Fetch in progress, or one that has started a Fetch since the previous round. On each shard it claims no more than Prefetch less that shard's share of what the source already holds (what it holds divided by the shards, rounded down), since a read takes up to Prefetch from each shard, and never more than Config.ClaimCount. A round that claims nothing, because the caller is not fetching or the source already holds Prefetch for every shard, sends one XPENDING per shard instead, so a server that stops answering still shows in Health. A busy runner's source used to claim a crashed consumer's expired entries into a buffer nothing drained, 128 per shard whatever Prefetch said, while the sources that were fetching went without them. The room was then Prefetch less everything the source held, which under a backlog on a partitioned topic was gone for all but a moment of each read's batch, so a nacked or abandoned message came back several sweep intervals late.
    • A small room does not shorten the search. XAUTOCLAIM looks at no more than ten pending entries for each one its COUNT lets it claim, so a round with room for one looked at ten, and an expired entry behind hundreds that live consumers keep fresh came back only after tens of rounds. The round's XPENDING has no such limit, and what it lists past where the XAUTOCLAIM stopped is claimed with XCLAIM. Once a round's XPENDING has seen every expired entry to the end of the pending list, the next round starts from the beginning of it rather than where the XAUTOCLAIM stopped.
    • Redelivery throughput follows Prefetch. A source now takes back at most Prefetch expired entries per shard per round (less its share of what it holds), where it used to take Config.ClaimCount. Both are 128 by default, so nothing changes there, but a source with a small Prefetch drains a crashed consumer's backlog slowly: with Prefetch 1 and the default interval, one entry per shard every 10 s. The sources that are fetching share that work, so more of them drain it faster.
    • The delayed mover runs every Config.MoverInterval, and only under the zset nack arm. Under the other three each sweep round releases what is due in the topic's sorted sets instead, one ZRANGEBYSCORE per shard, so a message parked while the subscription ran zsetmover still comes back once it runs another arm (the default included), to within the sweep interval, MoverCount (128 by default) due messages per shard a round, so a larger backlog takes several rounds. Such messages used to stay parked for good: acknowledged in the stream, and released only if a zsetmover source opened on the topic again. A failed release degrades Health as the mover's does. The sorted sets belong to the topic, not to a subscription, so a member no driver can decode (left in the set for an operator, as the mover leaves it) degrades Health for every source on the topic, of every subscription and arm. A read of a delayed set that the server's ACL refuses is no failure: a user without ZRANGEBYSCORE never ran the mover, so that shard is skipped, and a round whose only answer was such a refusal is a good one, which does not degrade Health and clears a release failure an earlier round recorded. A real failure of another shard in the same round is still reported. The read is still sent every round, one refused read per shard, which Redis groups into one ACL LOG entry with a count, so a grant takes effect at the next round without the source reopening. A refusal of the release script itself, by a user that may read the set but not ZSCORE, ZREM or XADD, degrades Health: the due messages are then stuck, and nothing is lost. A user that should release what an earlier zsetmover deployment parked needs ZRANGEBYSCORE, plus ZSCORE, ZREM and XADD inside the release script; a zsetmover user needs the same, with ZADD and XACK for the park. ZSCORE is new in this release: an ACL that lists commands one by one must add it, or releasing stops (the messages stay parked and Health says why).

    A delivery the sweep produced waits in the source's buffer until a Fetch takes it, and the buffer holds one delivery per entry: a later sweep that re-claims a buffered entry replaces it rather than queueing a second generation, because the older generation's settlement would be refused. A round in which one shard fails still buffers what the other shards claimed, and reports the failure through Health: the server has already handed those entries to this source, and dropping them left them pending until the next deadline, with an attempt too many.

    Waiting in the buffer is not an attempt. Before a round claims, it restarts the idle clocks of what the buffer holds with the extension a lease extension uses (see Why the extension is guarded too), which counts no delivery, so the round does not claim them again. Each round used to claim a waiting delivery again once it had waited a deadline, and every claim counted an attempt, so a message whose handler had died reached the next one counted as several attempts and could be dead-lettered before any handler had retried it. A source whose caller has stopped fetching keeps nothing fresh, so what it holds can be claimed by the sources that are fetching. When its caller comes back, a buffered delivery whose lease has run out is checked with the same extension before it is handed out. Under the default owner guard it is dropped if another consumer has claimed it. Under AckGuard: none the extension is a bare XCLAIM, which takes the entry back from that consumer, so both copies are handed out: that setting is safe only with a single consumer, and the old buffer handed the copy out as well.

    A buffered delivery's lease (DeliveryInfo.ReceivedAt and LeaseExpires) is counted from the read, the claim or the extension that last started the entry's idle clock, not from the Fetch that hands it out. Another consumer's sweep takes the entry a deadline after that, so a delivery that waited in the buffer can reach its handler with less than a whole deadline left.

    DeliveryInfo.Sequence is the entry identifier packed: the millisecond in the high bits and the within-millisecond sequence in the low twenty. It is monotone, so comparing two deliveries' sequences gives the publication order, and exact, so StartAtSequence resumes at the entry rather than at the start of its millisecond — which on a busy stream would re-deliver everything published in it. Above 2^20 entries in one millisecond the sequence saturates, which makes a resume start slightly early rather than slightly late.

    StartPosition Redis
    StartLatest (default) $ — the entries added from now on
    StartEarliest 0-0 — the beginning of whatever the stream still holds, which is not "every message ever published" if the stream was trimmed
    StartAt(t) <t in ms - 1>-18446744073709551615, the last identifier before t's millisecond. Redis has no seek-by-time; a stream identifier's high half IS the publication time, so this is a real position at millisecond resolution. XGROUP CREATE takes the last entry the group has seen, so the group's first delivery is the first entry of t's millisecond, the one published at t included
    StartAtSequence(n) the identifier immediately before the packed one: the one before it in its millisecond, or <ms - 1>-18446744073709551615 when n is the first entry of its millisecond. As with StartAt, XGROUP CREATE takes the last entry the group has seen, so the group's first delivery is the entry at n, as on the memory, Kafka and JetStream drivers

    Start positions apply when the consumer group is created. A group that already exists has a committed position and is left alone, which is the specification's idempotence; moving an existing one is Admin.Purge or a replay.

    AckBatch the same script over a batch of identifiers, one command per shard, pipelined

    Why the acknowledgement is guarded¶

    XACK removes a pending entry whoever is holding it. So

    consumer A reads entry E          (E pending, owner A)
A's handler is slow
consumer B runs XAUTOCLAIM        (E pending, owner B)
B starts processing E
A finishes and sends XACK E       (E leaves the pending list)
B crashes before finishing

    loses the message: A acknowledged work B was doing, B never finished it, and nothing will ever deliver E again. The specification calls that a disqualifier.

    Two mechanisms close it, because the two cases have different evidence:

    1. Within one source, a generation table. Every entry handed out is registered with a generation, and handing it out again — which is what the reclaim sweep does when a handler outlives its lease — supersedes the previous one. A settlement carrying the superseded generation is refused before any command is sent. Exact, and free.
    2. Across processes, the server's own pending row, which records the consumer holding the entry. Every source gets a consumer name unique to that instance, so "the row names somebody else" is exactly "somebody else claimed it" — and the guard checks it inside the same Lua script as the XACK, because checking it in the client and acknowledging afterwards leaves the window the check was for.

    The consumer name's uniqueness is therefore load-bearing and is not configurable: Config.ConsumerPrefix sets the prefix and the driver always appends a nonce. Two sources sharing a name would each believe the other's deliveries were their own.

    AckGuard: none turns (2) off: one command instead of one script call, and the loss window above open. It is correct only when nothing else reclaims from the same group, which in practice means a single consumer process.

    Why the extension is guarded too¶

    XCLAIM key group me 0 <id> JUSTID is a claim. min-idle 0 means "no matter how recently it was delivered", so an extension written as a bare XCLAIM takes the entry from its current holder and reports success — after which two consumers each believe the delivery is theirs. FuzzRedisReclaimer found that in 1.3 seconds.

    Extend's by argument is not sent. Redis has no "extend by": the lease is this driver's, its length is Config.AckDeadline, and what the extension does is reset the idle clock the deadline is measured from. JUSTID is what keeps it from incrementing the delivery counter, so extending a lease twenty times does not make a slow handler look like a message that keeps failing and trip the specification's MaxAttempts.

    So an extension buys one AckDeadline from now, and a by longer than the source's AckDeadline is refused with InvalidArgument before anything is sent. Accepting it would report the lease as moved, and the sweep would reclaim the entry one deadline later underneath the handler. A delivery the sweep has already handed out again answers ErrLeaseLost first, whatever it asked for.

    An entry trimmed or deleted from the stream has no lease left to extend on Redis 7.0 and later, where the extension's XCLAIM drops its pending row and returns nothing, so Extend answers ErrLeaseLost under either guard, which tells the handler to stop. The guarded script used to list the entry as extended without reading what its XCLAIM returned: Extend answered nil while the row went, and the settlement after it answered ErrLeaseLost. On 6.2 the XCLAIM keeps the row and the extension stands.

    Attempt counting¶

    DeliveryInfo.Attempt is the sum of two halves, and it has to be:

    • the broker counts — XAUTOCLAIM increments a pending entry's delivery counter, and the sweep reads the counter with an XPENDING pipelined alongside the claim. XAUTOCLAIM returns the entries and not their counters, so without the XPENDING every redelivery would report attempt 2 and MaxAttempts would never terminate;
    • a nack arm that re-adds the entry starts a new pending row whose counter begins again at one, so what was lost travels in the entry's x:a field and is added back.

    An entry that waits behind a stop hold is not claimed while it waits, so the wait is not counted: the sweep restarts its idle clock instead, and the entries a source gives back when the hold starts keep the attempt they had (see Delays).

    Ordering¶

    FeatureOrderedByPartition and FeatureOrderedByKey are conditional; FeatureOrderedGlobally is conditional for a one-shard topic and unsupported otherwise.

    A stream is a total order and a consumer group hands out entries in it, so one consumer of a subscription sees a shard in publication order. What breaks it, stated rather than omitted:

    • two consumers of one subscription interleave across the shard — that is what a consumer group is for;
    • two of the four nack arms re-add the entry under a new identifier, so a retried message is delivered after everything published since it failed. The capability note names the bound arm, so a program can ask rather than assume.

    Config.Partitions > 1 removes the global order: four shards are four independent total orders and nothing sequences them against each other. A key chooses its shard by FNV-1a over the key bytes, which is stable across processes and across restarts — a key that hashed differently in two publishers would put one key's messages in two shards and break per-key ordering with nothing failing.

    A message with no key goes to shard 0 rather than to a random or round-robin shard. The specification makes a keyless message unordered so any shard is correct, and shard 0 is the one that needs no hash; the cost is that a keyless workload on a partitioned topic does not spread.

    Delays¶

    Config.Nack Redelivery Delay Keeps position Pending list
    leavepending (default) the reclaim sweep, after one acknowledgement deadline refused yes one entry per in-flight message
    zsetmover a mover releases the parked entry when it is due arbitrary, to within MoverInterval no empty
    readd immediate refused no empty
    stop the reclaim sweep, and the shard is held until the entry is settled refused yes, strictly one entry per in-flight message

    A delay an arm cannot honour is refused with ErrUnsupported and settles nothing, which is the rule, and only zsetmover honours one. leavepending and stop redeliver when the reclaim sweep finds the entry idle for the deadline, whatever was asked, so they refuse every delay before anything is sent, and a runner that asked for one requeues at once instead. It does not hold the delivery for the delay, because this driver's negative settlement is emulated (mq.FeatureNack is EmulatedDurable) and a hold would hand out the entries behind it under stop (see A delay the driver cannot make). They used to accept a delay shorter than the deadline, on the grounds that arriving late is within "held back for at least this long": a 2-second delay came back 30 seconds later, while the capability table said it was refused. A nack under either arm sends nothing. The capability table answers Unsupported for DelayedRedelivery under leavepending, readd and stop (it said Conditional), with a note naming zsetmover, so Capabilities.Has and the runner see the refusal before any nack is sent.

    The zset arm's park is ZADD plus XACK in one Lua script and its release is ZSCORE, XADD and ZREM in another, so a crash cannot leave the message both pending and parked (a duplicate) or neither (a loss), and two movers racing over one due entry produce exactly one redelivery: a script runs with nothing interleaved, and the second finds the member gone.

    Every script writes the copy before it removes or acknowledges the original. A script is not a transaction: Redis keeps what a script wrote before a command that fails, and the ACL can refuse any one command inside it. The release used to ZREM the member and then XADD it, so a user who may ZREM but not XADD lost the message, gone from the sorted set and never in the stream. It now checks the member is there (ZSCORE, which the release did not send before, so an ACL that lists commands one by one must add it), removes nothing first (a ZREM of the empty member, which asks the ACL the ZREM's question before the XADD writes anything), writes the copy, and removes the member last. On a real 7.4, the old release as a user without XADD left the message in neither place; the new one leaves it parked, and as a user without ZREM leaves it parked with no copy. The re-add, the park and the dead-letter move already wrote first: a refused write leaves the entry pending and writes nothing, and a refused XACK leaves the copy written and the entry pending, a duplicate that is reported with an unknown outcome. It is advertised as EmulatedDurable with the condition stated: a parked entry lives in a sorted set, so it survives exactly what the append-only file or the snapshot preserves.

    A parked member carries the entry's source identifier, and that is not decoration: a sorted set is a set, so two identical messages parked for the same instant would otherwise be one member and one of them would be silently discarded.

    stop is the only arm with head-of-line blocking, and it is the point of the arm: nothing behind the failed message is delivered until it is settled, so a strictly ordered stream survives a retry. One poisonous message stops its shard until MaxAttempts dead-letters it.

    The hold covers more than the next read, because entries behind the failed message can already be on their way:

    • Every failed message of a shard holds it. When two fail before either is settled, the shard reads nothing new until both are, and the second is retried only after the first.
    • A fetch already waiting at the server when the nack lands is answered with whatever was published during its block. The source keeps those entries pending and hands them out after the retry, in order. Each sweep restarts their idle clocks, so the wait is not counted as an attempt and no other consumer claims them. A source under this arm sweeps at least every third of its own deadline for that reason, even when the backend's interval is longer. The read that hands them out restarts the clocks once more, so their leases start with that read.
    • Entries the source read but has not handed out yet (a read takes up to Prefetch, and a fetch hands out only as many as its caller has room for) go back to the shard's queue with the failed message. They stay pending, the sweep keeps their idle clocks fresh as it does for a waiting fetch's entries, and they are handed out after the retry, in order, as first attempts: no handler has tried them. The same goes for what a read or a sweep brings back while the nack lands, before the source has buffered it. An entry among them that cannot be decoded is dealt with at once instead, as Fetch would deal with it: it never reaches a handler, so it has no order to keep, and a hold on it would never be lifted.
    • With every shard held, Fetch waits for a settlement, a sweep round, its context or Close, at most one Block at a time, rather than going straight round its loop.
    • A failed message trimmed out of the stream (by MaxLen, XTRIM or XDEL) before its retry can never be delivered again, so its hold lifts at the next sweep and the source acknowledges its pending row. On Redis 6.2 the hold used to stop its shard for good: XAUTOCLAIM there claims a trimmed entry like any other and answers a null, so its row stays this consumer's. A retry already with its handler keeps the hold until it is settled or the source closes, so a handler that never settles or extends it keeps its shard held that long. On 7.x and 8.x the next XAUTOCLAIM drops such a retry's row at once however recently it was delivered, and the hold used to lift with it, so the message behind the retry went to a handler while the retry's still ran. The settlement is refused there with ErrLeaseLost, the row being gone, and the refusal ends the hold; with lease extension the handler's next Extend does, and tells the handler to stop. A handler whose settlement fails gives the hold up at the next sweep round, so it does not wait for a settlement nothing may make.

    Dead-letter queue¶

    There is no dead-letter destination unless the configuration names one, and a Reject without one reports ErrUnsupported and settles nothing. The capability table claims FeatureDeadLetter only when one is named, so Run refuses WithNativeDeadLetter at once on a backend with none. It used to claim it whatever the configuration said, so Run accepted the option and every poison message's dead-letter was refused and the message requeued for as long as the run lasted. That is worth stating first, because a driver that derived a destination from the topic's name — which this one did until the suite ran against a real server — makes a Reject succeed on a subscription nobody gave a destination to, and the message is moved to a key the operator has no consumer for.

    Setting Destination Move
    Config.DeadLetterSuffix {topic} + suffix one Lua script: copy and acknowledge in one step
    Config.DeadLetterTopic that topic's own key, with its own hash tag two commands, and a documented duplicate window
    neither none Reject is ErrUnsupported

    The script does not XDEL the entry from the source stream: a dead-letter is a decision about this subscription, and deleting the entry would remove it for every other consumer group on the topic.

    The copy leaves the source's bookkeeping behind: no x:a attempt count and no group stamp, so the dead-letter subscription's first delivery of it is attempt 1 and not a redelivery.

    The two-command form's window is the cost of a destination on another slot. A cluster refuses a script whose keys are on two slots (CROSSSLOT), so the move becomes XADD then the guarded XACK — and a crash between them leaves the message in the dead-letter stream and pending in the source, so it is dead-lettered twice. A deployment that cannot tolerate that uses DeadLetterSuffix, whose destination shares the topic's tag by construction. An acknowledgement that fails once the copy is in the dead-letter stream, for any reason, a dial the server refused included, leaves the move half done: the Reject reports an unknown outcome (ErrSettlementUnknown), so the core does not let it be repeated into a second copy, and the entry stays pending in the source. Earlier versions returned a refusal the server answered there as a definite failure, and a repeated Reject wrote the copy twice.

    An entry the source cannot decode is dead-lettered as soon as it is read, when a destination is configured, by the same move a Reject makes. It never reaches a handler, so MaxAttempts never counts it, and a later attempt cannot decode it either. With no destination it stays pending, the reclaim sweep brings it back every AckDeadline, and Health reports it as Degraded each time, until the source's next good sweep.

    Headers & limits¶

    FeatureNativeHeaders, FeatureBinaryHeaders and FeatureDuplicateHeaders are all native, which is not the usual answer for a broker with no header field. A stream entry is an ordered field-value list of binary-safe strings, so the entry layout carries the whole promise in the entry itself: positional h:<n> fields keep the order and allow a repeated key, and a RESP bulk string carries any byte.

    The consequence is the opposite of most drivers': the portable envelope is never needed here. MetadataAdaptive publishes exactly as MetadataNativeStrict does, and MetadataLenientDrop never drops anything. Only MetadataPortableEnvelope differs, and it differs because the caller asked for a wire format rather than because the driver needed one.

    Whether an entry is an envelope is never read off its body. An entry published under MetadataPortableEnvelope carries x:env = 1, a field only the driver writes (a caller's headers are h:<n> fields), and the dead-letter copy, the re-add and the delayed park keep it. A MetadataAdaptive consumer decodes an entry that carries it and delivers every other entry as it is, whatever its body looks like; a MetadataPortableEnvelope consumer decodes every entry. Both adaptive halves used to sniff the body: a native body that was a valid envelope reached an adaptive consumer as the message inside it, with a body, an identifier and headers (reserved ones included) chosen by whoever wrote the payload, and an adaptive publisher enveloped a body that began like one, so a strict or non-iqmq consumer read envelope bytes with the key and headers gone. drivers/redis/goredis shares the code.

    Upgrading from v1.1.3 or earlier

    An entry an earlier version enveloped carries no x:env, and nothing else in it says it is an envelope: it holds b and t, as a native publication with no key and no headers does. So an upgraded MetadataAdaptive consumer delivers it as it is, the envelope's own bytes as the payload with no key and no headers, and nothing reports it. Such entries are wherever an earlier version wrote them or a copy carried them: the topic's streams, its dead-letter topic (a dead-letter copy keeps the fields as written, whichever version made it), messages parked under zsetmover, re-added copies, and the history a new subscription or a seek replays.

    • A topic whose producers all publish MetadataPortableEnvelope needs no drain if its consumers read it with MetadataPortableEnvelope, which decodes every entry, old and new alike, whichever side upgrades first. An old consumer also reads an upgraded MetadataPortableEnvelope producer correctly, because it skips every x: field. What breaks is a MetadataAdaptive consumer of such a topic: switch it to MetadataPortableEnvelope before it upgrades, or upgrade it only once no unmarked entry is left anywhere above.
    • A MetadataAdaptive producer whose bodies can begin like an envelope (the magic IQMQ and a known layout byte) has no safe order. An earlier version enveloped such a body and an upgraded one publishes it natively, so an upgraded consumer reads an old entry as envelope bytes, and an old consumer reads a new entry whose body is a valid envelope as the message inside it. Drain everything above first, or stop every producer and consumer of the topic and start them together on the new version.
    • Strict and lenient producers and consumers are unaffected, and so are adaptive ones whose bodies never begin like an envelope: earlier versions published those natively too.

    There is no setting that reads unmarked entries as envelopes under MetadataAdaptive: deciding from the body is the defect this change removes.

    That mode is also the driver's one real limit, and it is checked before any I/O in every mode. driverkit.Envelope encodes anything and decodes under wire.Limits, so a message admitted above those bounds is published successfully and then breaks every Fetch on that subscription for ever — an unsettleable record the driver made out of a publication it accepted. The bound is wire.DefaultLimits, field for field, applied in every mode so that a message accepted in one is accepted in all:

    Bound Value
    key 64 KiB
    body 64 MiB
    identifier 256 B
    headers 1024
    header key 256 B
    header value 64 KiB
    string property 4 KiB
    logical topic 512 B

    Plus one that is not a length: the identifier, every header key and every string property must be valid UTF-8, because the envelope's decoder validates them and its encoder does not. FuzzRedisFields found that in a tenth of a second. Header values, the key and the body are not checked: the envelope carries those as bytes.

    Capabilities.Limits advertises the message size and the header count, which are the two has fields for. Redis's own proto-max-bulk-len (512 MiB by default) is not advertised: it is a server setting this driver does not read, and the specification forbids advertising a default as a fact.

    A topic name may not contain {, }, a carriage return or a newline: the first two would break the hash tag and put a topic's shards on different slots, and the last two break every operator tool that reads a key list.

    Reconnect¶

    What the driver does do is recover from the one thing a reconnection breaks: an empty script cache. A server that restarted, failed over or ran SCRIPT FLUSH has forgotten every script, and every settlement route here is an EVALSHA — the guarded acknowledgement, the guarded extension, the dead-letter move, the delayed park, the delayed release, the re-add. A NOSCRIPT is answered by sending the command again as EVAL with the script's body, on every route, because a driver that recovered on only some of them would stop being able to acknowledge anything after a failover while still being able to publish. EVAL carries the command's own keys, so on a cluster it reaches the node whose cache was empty, and that node caches the script as it runs it. A SCRIPT LOAD names no key, so a cluster client sends it to any node, and the node that answered NOSCRIPT could stay empty. In a pipeline only the commands that met NOSCRIPT are retried: the others succeeded, and re-sending an XADD is a second copy of the message.

    Health (the specification) reports Connecting, then Ready, and goes Degraded on three background failures, each of which is invisible from the caller's side:

    • a reclaim sweep that failed. The sweep is the only thing that redelivers, so a sweep that keeps failing is a subscription that has silently stopped being at-least-once.
    • an entry that cannot be decoded. It is a record in the stream that nothing can deliver; it is dead-lettered, or left pending when there is no destination, rather than being delivered as an empty message. It counts as a failed sweep until the source's next good one.
    • a delayed mover that failed. It is a parked redelivery that is not happening.

    It is Ready again once no open source's sweep or mover is failing: each one that failed has had a good round since, or its source has closed. A good round of one source says nothing about another's, so a source that keeps failing beside a healthy one keeps the backend Degraded, naming the latest failure of a loop that is still failing. Each return to Ready calls Hooks.OnReconnect. Health used to stay Degraded for the rest of the backend's life after a single failed round, and OnReconnect never fired again.

    OnReconnect runs on the goroutine that brought the health back: the sweep or mover of the source that recovered, or the Source.Close that removed the last failing source (then nothing reconnected). Like every hook it must not block, and it must not close the consumer or the client: their Close waits for that sweep or mover, which is running the hook.

    At-least-once window¶

    A delivery is at-least-once between XREADGROUP and the guarded XACK. Inside that window:

    • the message is duplicated if the handler completes and the acknowledgement's round trip fails, or if the handler outlives Config.AckDeadline and the sweep redelivers while it is still running;
    • the message is NOT lost if the consumer dies: the entry stays in the pending-entries list and the sweep — this consumer's successor, or another consumer — claims it once it has been idle for the deadline;
    • the message is NOT acknowledged by somebody else's mistake: that is what the guard is for, and AckGuard: none is the setting that gives it up.

    The worst-case redelivery latency to a consumer that is fetching is AckDeadline + ClaimInterval plus the rest of the read its Fetch is parked in, which is no longer than min(Block, ClaimInterval) (by default 30 s + 10 s + 5 s): the entry becomes claimable at the deadline, the sweep notices at its next pass however many fresh entries are ahead of it in the pending list, and the parked read hands over what the sweep claimed when it returns. A backlog does not hold the pass up: a source fetching from a partitioned topic has room on every shard until it holds Prefetch for each of them, and a read leaves that much only until the Fetch that made it takes its share.

    Close abandons rather than requeues, and that is the honest answer rather than the convenient one. There is no "unclaim" command: an unsettled entry stays in the pending list and becomes claimable once it has been idle for the deadline, so another consumer's sweep picks it up. The one command that would look like a prompt hand-back — XGROUP DELCONSUMER — deletes the entries along with the consumer, so it runs only when the pending list is empty.

    A consumer closed while its read is parked removes its row. That is the normal state of a consumer of a quiet topic: its Receive, or its runner's fetch, is parked in XREADGROUP. The tidy-up waits for that read first, because a read in flight may yet make the consumer the owner of entries. rueidis ends a read whose context has no deadline at once. A read under a deadline on rueidis, and every read on goredis, is waited for until the server answers it at the end of its block: such a close takes up to one Config.Block (five seconds by default), and never more than its own bound. Closing consumers one at a time with ConsumerHandle.Close adds those waits up, up to a block each; Client.Close closes them under one shared bound (below). The tidy-up used to find the read in flight and leave the row, whether the consumer was closed by ConsumerHandle.Close, Shutdown or Client.Close, so every restart of an idle service added a row per consumer for good.

    The pending-list check and XGROUP DELCONSUMER are one script, so a consumer is removed only when it holds nothing at that instant. They were two round trips, and an entry the server handed to the closing consumer between them was deleted with it: rueidis ends a parked read by closing its connection, and a server busy for a moment (a slow command, a fork, load) could run the tidy-up's check and a publication's XADD before it noticed the closed connection, serving that XADD's entry to the read it still had blocked. A read the server serves after the script makes the consumer again with the entry pending to it, which the sweep of the subscription's other consumers claims a deadline later: a row left and a redelivery, not a lost message. A user that may not run scripts (EVALSHA, and EVAL when the server's cache is empty) cannot remove its consumers: Close leaves the row and reports CodeForbidden, naming the script.

    Closing against a server that has stopped answering takes one bound, not one per source. A source's close on its own stops waiting after five seconds. Once the backend begins to close, from Client.Close (through BeginClose), Client.Shutdown or Backend.Close, every source's close shares one bound, five seconds from then:

    • A Fetch starts only a read that ends within the bound, so the consumers Client.Close has not reached yet stop reading new entries (at the default block, at once) and hand out only what they hold.
    • The sweep and mover rounds end by the bound, and none starts after it. A round is bounded by five seconds anyway, as well as by its interval.
    • A close waits for its read in flight until the bound and one second after it, a second all the sources share, or until the read is due back (its block and a second), whichever comes first.
    • The tidy-up gets at least a second for its round trip while no tidy-up has run out of time. One that ran out of a second or more, or a read not back when it was due, says the server is not answering, and every later tidy-up gets the passed bound and leaves its row.

    So against a server that answers nothing the sources' closes take the five seconds and at most a second more, on either client. Closing a client the driver dialled itself then closes rueidis's connections too, and rueidis waits up to a second for each connection still holding a command, which comes on top: Client.Close of 8 consumers against a paused server took 9 seconds on rueidis (4 of them rueidis's own close, as at v1.1.2) and 5 on goredis. On a server that answers it takes the longest read it waits for (at most a block) and a round trip per source, and removes every row.

    A source's close used to wait out its sweep round, up to a sweep interval, and then five seconds of its own, one source after another, so a backend with four sources took about a minute at the defaults. go-redis does not end a sweep round when its context is cancelled, only at its deadline, so on goredis the closes waited out a round each. One tidy-up that started in the bound's last moments, with less left than a server some distance away takes to answer, ran out of it, read as a server not answering, and left every later source's row behind. And while Client.Close closed its consumers one after another, the ones it had not reached kept starting reads that their closes then waited for, a second each after the bound, and gave up on: 16 idle consumers took 18 seconds on goredis and left 12 rows.

    BeginClose starts that bound and does little else, which is not all mq.ClosingBackend describes. As the contract says, it returns at once, reports nothing, and leaves a client you lent open. It does not end what the client holds for a server that is not answering: a publication or a settlement waiting for its reply waits for its own bound (its context, the durable bound, or rueidis's connection timeout), because closing the connection would also end the closes that follow, which need it. It does not stop rueidis reconnecting, and an operation that arrives after it waits for a connection rather than being answered at once. Sources and sinks work until each one's own close, except that a Fetch starts no read that would outlast the bound. The root only calls the method, so this changes nothing a close reports.

    Durability is the server's. ConfirmAccepted means the entry is in memory; a server that has not fsynced and then loses power loses it. ConfirmDurable is the boundary that says otherwise, and it needs an append-only file.

    FeatureDurableStorage follows what the server keeps across a restart, which the driver reads at open (CONFIG GET appendonly, then CONFIG GET save when that is no):

    Server FeatureDurableStorage
    appendonly yes Native
    appendonly no, snapshots configured Conditional: an entry survives as far as the last RDB snapshot
    appendonly no, save "" Unsupported: a restart empties the server
    CONFIG refused (a managed Redis, an ACL) Conditional: the driver cannot tell

    Redis's own default (appendonly no with snapshots) and a managed Redis that refuses CONFIG are therefore Conditional, and a program that requires RequireAtLeast(FeatureDurableStorage, Native) fails at construction there. It was Native whatever the answer, so that requirement was met by a server that keeps nothing, and a confirmed publication was gone after a restart. The claim is read once, when the backend opens, as FeatureDurableConfirm is: a CONFIG SET afterwards does not change it.

    A parameter this driver does not have is a construction error naming it, not a setting nobody notices was ignored. insecureskipverify=true without tls=true is refused: the alternative is a connection that dialled in the clear after the operator asked to skip verification. A typed Config with InsecureSkipVerify beside TLS skips verification as the DSN does, on a copy of your *tls.Config. It used to be ignored there, while String() and DSN() rendered it as on.

    Config.String(), Config.LogValue() and Config.DSN() all redact the credential. Anything a typed Config cannot carry — a Sentinel configuration, a custom dialler, client-side caching, an authentication callback — is reached through OpenWithClient, where the caller builds the rueidis.Client and says who closes it.

    Trimming is explicit. MaxLen is zero by default, because a stream is a log and a driver that trimmed by default would delete a subscription's unread messages to save memory nobody said was short. When it is set it is the approximate form (MAXLEN ~ n): exact trimming walks the whole radix tree, which is a latency spike on the publish path.

    Known gotchas¶

    • A topic is one cluster slot. Partitions do not spread a topic across nodes. See Topic / subscription mapping.
    • Config.Partitions has no server-side record. Changing it re-hashes every key.
    • StartEarliest is not "every message ever published" — it is the beginning of whatever the stream still holds, and a trimmed stream has forgotten the rest.
    • A consumer row per source instance. The consumer name carries a nonce, so XINFO CONSUMERS grows with the number of sources a process has opened. Close removes the row when the source holds nothing pending, also when its read was parked at the server. A source that closed with entries in flight leaves its row, and so do a close that ran out of its bound (a server that was not answering, or a read it could not end whose block outlasted what was left of the bound), a read the server served after the removal (it makes the consumer again, with that entry pending), and a user that may not run scripts. The name is that instance's own, so nothing removes the row afterwards. An operator who sees a long list is seeing crashed processes and closes like those, which is information rather than a leak.
    • Admin.DeleteSubscription is destructive in a way DeleteTopic is not. XGROUP DESTROY removes the group's pending-entries list with the group, so every message that subscription had been handed and not settled is forgotten. The messages stay in the stream for other subscriptions.
    • A topic whose stream does not exist is not found everywhere. Redis answers NOGROUP for a missing stream only from the commands that read a group. Every XGROUP subcommand answers "requires the key to exist", and XINFO "no such key". The driver reads all three as the stream being missing: a source opened with AutoCreate off is refused with the error that names AutoCreate, Admin.DeleteSubscription succeeds, and Admin.Purge and Admin.Stats answer CodeNotFound. It used to match NOGROUP alone, so against a server all four came out as CodeUnknown, or failed, and only the in-memory server the unit tests run on answered as the driver expected.
    • Admin.Purge does not touch the pending list, deliberately: a purge is about what has not been delivered, and a pending entry has been delivered and is somebody's in-flight work.
    • Admin.Stats's lag can be unknown. Redis reports a nil lag after an XDEL or an XTRIM made the count unreliable, and Redis 6.2 reports no lag at all (the field arrived in 7.0). The specification's Limit[T] is how that is reported rather than as a zero, so on 6.2 Depth and Lag are always unknown and InFlight is still a number.
    • An entry trimmed while it was pending. Redis 7.0's XAUTOCLAIM drops its pending row and reports the identifier, and the driver forgets it. An XCLAIM from a round's second round trip drops such a row too, on 7.x and 8.x, but names it nowhere; the row leaves Stats.InFlight at once, and a handler that still has the entry gets ErrLeaseLost when it settles it. Only a round for a fetching caller sends XAUTOCLAIM, so while every source of the subscription is open but not fetching such rows stay, and count in Stats.InFlight, until a source fetches again. On 6.2 there is no such reply element, so such an entry stays in the pending list for ever. That is the pending-list growth the specification asks about, and it is a reason to prefer 7.x. On 6.2 the row also counts in Stats.InFlight for ever, a sweep round for a caller that is fetching claims it again each deadline (it takes a place in the round's claim and delivers nothing), and the source that claimed it last closes owning it, so that source's consumer row stays in XINFO CONSUMERS: three trimmed rows and three source instances in turn left three rows behind. The exception is a failed message the stop arm holds its shard for, which the source looks up in the stream and acknowledges once it is gone, on either version.
    • Admin.ListTopics under a KeyPrefix holding *, ?, [ or \. SCAN's MATCH reads those as pattern operators, so the pattern stops at the first of them and the driver leaves out the keys of other prefixes that share the text before it. With KeyPrefix: "env[a]:" the listing used to be empty, with no error.
    • Request/reply is unsupported. Redis Streams has no reply channel, and building one out of a second stream per request would be a feature this driver invented rather than a broker capability.
    • Wildcard subscriptions are unsupported. Redis's pattern subscription is pub/sub, which has no consumer groups, no pending list and no acknowledgement.
    • The go-redis arm handles contexts differently. A Fetch cancelled without a deadline returns when its block ends rather than at once, an Ack or Nack cancelled that way returns when the server answers or the client's ReadTimeout passes, and a go-redis client you pass in needs ContextTimeoutEnabled for a deadline to reach the socket. Neither arm retries a command this driver sends; on the go-redis arm that holds whatever a client's MaxRetries says, a cluster client included. The go-redis arm refuses a redis.Ring: a Ring moves a topic to another shard while the topic's own is down, and a publication in that window reached no subscriber. Use a Redis Cluster, or one backend per server. See goredis.

    Driver-specific critical tests¶

    • FuzzRedisReclaimer (internal/streams) — two consumers of one group against one server, interleaving reads, sweeps, acknowledgements, nacks, extensions and clock jumps.
